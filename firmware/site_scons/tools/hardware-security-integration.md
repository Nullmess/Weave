# Hardware security integration — 1.0.4 source candidate

The policy code in `applications/services/weave/weave_hardware_policy.{h,c}` is internal and not an SDK contract. Neither `WEAVE_CAP_HARDWARE_ANTI_ROLLBACK` nor `WEAVE_CAP_MEMORY_ISOLATION` may be set. The native FAP loader still runs privileged tasks.

## Protected anchor

A production backend must implement protected, durable, atomic compare-and-advance of a generation and SHA-256 digest, scoped to a provisioned object. A monotonic integer alone does not prevent replacement by a different valid record at the same generation. The backend must reject unauthorized changes and prevent reset, replay and cloning. No ordinary SD/flash file or volatile test double qualifies.

The trusted coordinator must authenticate a candidate including its scope, generation and digest, write and verify the exact candidate durably, then commit the protected anchor. Recovery must read the anchor again if acknowledgement is lost. The previously committed bytes must remain recoverable until the anchor advances. If the anchor points to missing or altered data, fail closed; do not roll back automatically. Provisioning, deletion/tombstones and migration must themselves be protected. A production firmware anti-rollback scheme also needs an authenticated immutable boot path that checks the anchor before execution, including DFU/recovery/update paths. The present DFU path can enter system ROM; no such enforced chain has been demonstrated. Do not program OTP, change option bytes, disable recovery or lock debug access based on this source candidate.

The internal `weave_trusted_record` coordinator implements this ordering over two durable slots per scope (slot index = generation modulo two). It verifies the active slot before staging, hashes and authenticates the candidate, reads back the staged record before advancing the anchor, and wipes temporary buffers. Recovery selects only the slot matching the protected anchor; it does not select the highest generation on disk. A lost acknowledgement can be retried idempotently. The caller must serialize each scope and provide trusted SHA-256, an authenticated/protected anchor backend and durable slot I/O. The coordinator is not wired into the ordinary vault or firmware update paths. It does not provision an anchor, and it cannot prevent concurrent writes by another privileged actor or guarantee physical durability of a dishonest backend.

## MPU integration

The existing HAL MPU code protects null access and stack guards, but does not isolate native FAPs. `configENABLE_MPU` is intentionally unchanged and `freertos.scons` still selects the non-MPU ARM_CM4F port. Enabling the bit alone is unsafe. The tested layout policy validates four disjoint exact MPU regions in an exclusively reserved RAM arena: code RX, read-only data R/XN, mutable data RW/XN, and stack RW/XN. The internal encoder additionally prepares ARMv7-M RBAR/RASR values for four regions (RX, R/XN, RW/XN, RW/XN) and rejects collisions with reserved region indices or an insufficient region budget. It does not program the MPU. This is only a layout/descriptor check. The port must program and switch these regions, allocate suitably aligned exclusive memory, ensure privileged kernel memory is not mapped, and enforce unprivileged execution. It must also account for the STM32WB region budget and privileged static regions, validate the ELF loader and relocation rules, provide a constrained syscall ABI with checked copy-in/copy-out and validated handles, mediate all DMA and peripheral access, keep callbacks out of privileged context, and terminate tasks safely on faults. Legacy privileged FAPs can still bypass software boundaries and must not coexist with a claimed hostile-code isolation guarantee unless they are explicitly trusted. Compatibility with existing exported native APIs cannot be assumed.

## Validation

Run `python firmware/site_scons/tools/tests/test_hardware_policy.py` from the repository root. The tests exercise actual policy and HAL source using synthetic backends/register interfaces with ASan and UBSan. They are not electrical or on-target tests. Compile the full firmware using the original dependency bootstrap and toolchain on a connected host. The archive omits upstream dependency sources; `weave_deps.py` fetches them from the configured upstream ref and checks Monocypher's release hash. A real device and an approved threat model and provisioning/recovery design are required to verify the protected anchor and MPU integration. The release gate remains closed until evidence for every required check is recorded.
